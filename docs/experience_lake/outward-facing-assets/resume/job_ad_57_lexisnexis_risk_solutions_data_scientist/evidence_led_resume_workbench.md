# LexisNexis Risk Solutions Data Scientist - 3 Screens

This is the job-ad interpretation stage only: business/risk problem screen, technical/model capability screen, and stakeholder/operating-style screen. No proof buckets, evidence ledger, scoring, or bullets yet.

## 1. Business / Risk Problem Screen

This is a **fraud/risk Data Scientist** role, not a general Data Scientist role.

LexisNexis Risk Solutions works across AML/CTF, identity authentication and verification, fraud, credit risk mitigation and customer data management. The team uses global data from a large real-time fraud detection platform, and the role is expected to create real-world impact through **lower customer friction, reduced fraud losses and increased customer profitability**. The platform analyses billions of transactions per month across financial services, insurance, e-commerce and on-demand services.

So the CV eventually needs to prove evidence around:

| LexisNexis business/risk problem | What the CV needs to show later |
| --- | --- |
| Fraud loss reduction | You can identify, rank, score or flag risky behaviours, transactions, accounts or cases. |
| Customer friction reduction | You understand the trade-off between catching fraud and not blocking good customers. |
| Customer profitability | You can connect fraud/risk decisions to value, cost exposure, false positives or review burden. |
| Real-time fraud detection | You have evidence of scoring, monitoring, streaming/near-real-time decisioning or production-shaped fraud workflows. |
| Enterprise customer risk problems | You can package analysis into validation reports, risk summaries, presentations or model rationale. |
| Evolving fraudster behaviour | You can define behavioural features that capture account, transaction, usage or anomaly patterns. |
| Financial services / e-commerce / payments risk | You can speak through concrete fraud, transaction, payment, chargeback, account or behaviour evidence. |

The strongest business-positioning phrase is likely:

```text
fraud-risk data science for real-time decisioning, behavioural features, model/rule evaluation and customer-friction trade-offs
```

Not:

```text
generic machine learning
business intelligence reporting
customer analytics
commercial KPI dashboards
```

# Grounding Dictionary - LexisNexis

Before drafting, these meanings must be locked.

## "Fraud-Risk Model"

Do not write:

```text
fraud-risk model
```

unless we can say:

```text
model type = supervised classifier / anomaly detector / hybrid risk score
entity scored = account / transaction / customer / session / case
target label = known-risk / fraud flag / rule-triggered / chargeback-linked / manually reviewed suspicious record
metric = recall / precision / lift / AUC / top-band capture / false-positive proxy
```

## "Fraudster Behaviour Features"

Do not write:

```text
features that capture fraudster behaviour
```

without feature names.

Ground it as:

```text
velocity features
transaction-frequency features
account-age features
failed-action features
usage anomaly features
session/device/channel features
score-band behaviour features
```

## "Rule-Based Model"

Do not write:

```text
rule-based model
```

unless we can name:

```text
rule = threshold / trigger / risk indicator / rule table
baseline = existing rule / manual review / broad threshold
comparison = known-risk capture / false-positive proxy / review volume
```

## "Customer Friction"

Do not write:

```text
reduced customer friction
```

unless measured.

Safer:

```text
false-positive proxy
low-risk records flagged
review-volume table
non-risk accounts in top score band
threshold trade-off table
```

## "Fraud Losses / Profitability"

Do not write:

```text
reduced fraud losses / increased profitability
```

unless measured.

Safer:

```text
cost exposure
transaction value at risk
risk-adjusted value proxy
chargeback/dispute exposure
high-value high-risk segment
```

## "Production Deployment / MLOps"

Do not write:

```text
production deployment / MLOps
```

unless the artefact exists.

Ground it as:

```text
AWS scoring service
batch scoring job
streaming decisioning workflow
CI/CD workflow
versioned configs
deployment checklist
rollback process
monitoring dashboard
scoring logs
```

## "ML Monitoring"

Do not write:

```text
model monitoring
```

unless it monitors model inputs/outputs.

Ground it as:

```text
feature drift check
score distribution check
data freshness check
performance decay check
score stability report
failed scoring run log
```

## "External / Executive Presentation"

Do not write:

```text
customer-facing presentation
```

unless true.

Ground it as:

```text
fraud-risk readout
model validation deck
risk-driver report
threshold recommendation table
executive-style portfolio presentation
```

# Key Blanks Before Scoring

```text
1. What was the fraud/risk target label?
2. What exact fraud/risk features existed?
3. Was the score ML, rules, or hybrid?
4. What baseline did we compare against?
5. What is the strongest fraud metric: lift, recall, top-band capture, false-positive proxy?
6. What was deployed: scoring service, batch job, streaming workflow, dashboard, case queue?
7. What monitoring existed: drift, score stability, freshness, refresh checks?
8. What case-management output existed?
9. What value/cost exposure metric is defensible?
10. What presentation/report artefact can prove customer/executive-style communication?
```

The next step is **evidence scoring**. Be strict: platform fraud-risk/MLOps evidence should lead; generic dashboards, academic modelling and operational Excel evidence should only support if they sharpen the LexisNexis story.
