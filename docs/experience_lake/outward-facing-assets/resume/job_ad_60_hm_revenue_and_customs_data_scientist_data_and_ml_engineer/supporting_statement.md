# Supporting Statement - HM Revenue and Customs - Data Scientist (Data and ML Engineer)

## 750-word personal statement - Essential Criteria

My experience fits this role through three connected areas: building a deployed data and machine learning platform, managing operational data products, and explaining technical outputs to mixed audiences. In my independent fraud and transaction decisioning platform, I designed, wrote and iterated Python, SQL and SAS code from early notebooks and scripts into a deployed AWS platform with ingestion, validation, feature creation, rule and model decisioning, case creation, scheduled jobs, monitored services, access controls and offline evaluation.

The platform started as a prototype that could score sample transactions, but I rebuilt it into separate components so it could be operated repeatedly. Python services handled ingestion, validation, APIs, orchestration and scoring logic. SQL transformations supported querying, joins, data checks and curated analytical views. SAS programmes supported repeatable analytical processing and controlled dataset preparation. I used Git and GitHub to track changes to validation logic, feature definitions, thresholds, model evaluation and dashboard measures. I also used command-line workflows, environment configuration, secrets handling and controlled access so credentials were not hard-coded into the codebase. To make outputs accessible to users, I used clear status labels, reason codes, dashboard fields and separate data-quality flags so a user could understand whether a case reflected suspicious behaviour, missing data or a validation issue.

I have practical experience integrating and separating data feeds to produce tested data products. In an operational Data Analyst role, I worked with Oracle data extracts, SAS programmes, QHSE trackers, equipment movement notes, man-hour records and close-out files. I separated raw extracts, cleaned datasets, exception views and final reporting outputs so managers could see which jobs were active, delayed, field-completed, awaiting documentation, awaiting equipment confirmation or ready for close-out. I tested outputs using row counts, duplicate checks, missing-field checks, status logic, reconciliation between sources and review of unexpected changes. This made recurring reporting more reliable and reduced repeated manual checking.

I applied the same data development discipline in the fraud platform by creating reusable data layers for raw events, validated events, context projections, feature tables, decision outputs, case records, labels, monitoring outputs and evidence. Services, dashboards and analysis workflows could use trusted data without going back to raw sources each time. This supported data reuse and made it easier to trace a dashboard measure, decision or model evaluation back to its source.

Testing and deployment risk were central to the platform. I checked required fields, timestamps, duplicate events, unexpected categories, impossible values, failed joins, row-count movements, model score distributions, threshold effects, false positives, false negatives and drift indicators. I monitored scheduled jobs, logs and dashboard refreshes so that a stale dashboard, failed transformation or broken data feed would not be mistaken for a genuine business trend. I documented assumptions, validation rules, feature definitions, known risks, dashboard measures and interpretation limits.

I have also communicated technical issues to non-technical stakeholders in multidisciplinary settings. In the Data Analyst role, I supported weekly operations and close-out discussions with operations, equipment, QHSE, admin, commercial colleagues and managers. Different teams used terms such as "completed" differently, so I prepared focused exception views rather than raw data dumps. I translated findings into practical questions: whether a signed service report had been received, whether equipment had returned, whether a delay related to client approval, documentation, logistics or internal follow-up. This helped the group agree what needed action and improved the report through feedback from the people closest to the work.

My work has contributed to data science delivery for business problems. The fraud platform was built to reduce manual review burden, prioritise suspicious events, explain why cases were flagged and evaluate whether rules and models were performing responsibly. My postgraduate data science research also strengthened my technical base: I processed high-frequency smartphone sensor data, created model-ready windows, trained deep learning models and evaluated outputs using accuracy, precision, recall and F1-score while documenting limitations around sampling, class balance and generalisability.

I have grown my own capability through postgraduate data science training and through building the platform, where I learned cloud deployment, Python services, SQL transformations, SAS processing, monitoring, access control and machine learning evaluation as practical requirements. I have also developed others by walking placement students and junior trainees through reporting workbooks, Excel checks, operational definitions and exception interpretation, and by training new starters in a fast-paced frontline role where clear instructions, checking understanding and correcting errors patiently were essential.

## 250-word desirable criteria section

I understand data protection regulations as the lawful, fair, secure and proportionate use of personal data. My working understanding of UK GDPR covers purpose limitation, data minimisation, accuracy, storage limitation, integrity, confidentiality and accountability. In my fraud decisioning platform, I applied these principles by separating raw transaction events from curated analytical outputs, limiting access to sensitive data layers, exposing aggregate monitoring where record-level detail was not needed, keeping credentials out of code, documenting lineage and making validation failures visible.

I have hands-on experience with version control tools, the command line and integrated development environments. I used Git and GitHub to manage code changes, make iterations traceable, and control changes to validation logic, feature definitions, model evaluation and dashboard measures. I used the command line to run scripts, manage environments, work with repositories and carry out deployment tasks. I used integrated development environments to write Python services, manage configuration, debug code and move work from notebooks into maintainable scripts and deployed services.

I also have practical cloud architecture experience through my deployed AWS fraud and transaction decisioning platform. I used API Gateway, Lambda and MSK Serverless for controlled ingress, validation and event transport; EKS for platform services; Aurora PostgreSQL and S3 for runtime state, object storage and evidence; SSM Parameter Store and IAM for configuration and access control; CloudWatch for logs, metrics and alarms; and SageMaker, Databricks and MLflow for learning, evaluation and model lineage.
