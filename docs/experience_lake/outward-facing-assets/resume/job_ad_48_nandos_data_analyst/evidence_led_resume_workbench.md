# Nando’s — Data Analyst: 3 Screens

## 1. Business / problem screen

Nando’s is **not primarily hiring a reporting analyst who only builds dashboards on request**. The job ad frames the role as part of the Data and Analysis Team, helping the business get the right information at the right time and get better value from its data to achieve business goals. It also says the role is broader than conventional reporting, combining SQL modelling, pipeline support, Looker reporting, business-problem translation, data quality, documentation, automation, and contribution to a more mature cloud data environment.

So the CV must eventually prove evidence around:

| Nando’s business problem | What the CV needs to show |
| --- | --- |
| Reliable business information | You can create trusted data outputs people can use repeatedly, not one-off analysis only. |
| Single source of accurate, timely data | You can help standardise definitions, models, dashboards, and reporting layers. |
| Self-serve insight | You can build dashboards/reports that let teams answer recurring questions without manual analyst dependency. |
| Business-problem translation | You can understand the “why” behind a request and turn ambiguous questions into scoped analytical work. |
| Performance insight for support teams and restaurants | You can give operational/business teams clear views of KPIs, issues, and performance. |
| Data maturity | You can contribute to better data quality, documentation, governance, testing, and automation. |
| Cross-domain analysis | You can work across finance, operations, kitchen tech, stock, and other business areas. |

The strongest business-positioning phrase for Nando’s is probably:

```text
cloud data modelling, self-serve BI and business-facing analytics for a maturing data environment
```

Not:

```text
payments, fraud and chargeback analytics
```

And not:

```text
customer behaviour ML platform
```

Those may be useful evidence sources later, but they are **not the centre of gravity** for this role.

## 2. Technical / capability screen

Technically, this role is much more **analytics engineering + BI + data quality** than generic analysis. Nando’s asks for complex SQL, Dataform or similar transformation tools, cloud data platform work, Looker dashboards, pipeline support, Git, testing, documentation, governance, and automation.

| --- | --- |
| Complex SQL | SQL models, CTEs, window functions, joins, transformations, reusable views/tables. |
| Dataform / dbt / similar transformation work | Dataform-style SQL models, dbt-style transformations, model dependencies, transformation-layer ownership. |
| Cloud data platform | BigQuery, Snowflake, cloud-hosted datasets, source tables, modelled reporting layers. |
| Pipeline collaboration | Supporting data engineers with pipeline design, testing, validation, or downstream model requirements. |
| Looker / BI dashboards | Looker dashboards, Looker explores, KPI dashboards, self-serve reports, dashboard iteration. |
| Data quality and testing | Data-quality checks, validation queries, reconciliation checks, test cases, issue detection. |
| Documentation and lineage | Documented model definitions, KPI logic, lineage, data limitations, dashboard definitions. |

| Automation | Automated manual reporting tasks, refresh processes, validation checks, recurring workflows. |
| Statistical judgement | Using appropriate statistical methods when analysis requires more than descriptive reporting. |

For this CV, **SQL modelling and data-quality discipline are not supporting details**. They are central evidence.

So eventual CV language should probably name artefacts like:

Not vague phrases like:

```text

business reporting

```

Those are too generic for this role.

## 3. Working-style / stakeholder screen

Nando’s wants someone who can work independently across the full data stack while still operating in a collaborative team. The ad stresses communication with technical and non-technical stakeholders, comfort with ambiguity, product mindset, curiosity, proactive improvement, peer review, knowledge sharing, and thoughtful AI use inside a governed data environment.

| Working-style requirement | CV evidence we should look for later |
| --- | --- |
| Product mindset | Evidence that you understood the business objective before building the analysis or dashboard. |
| Ambiguity handling | Examples where a vague request became a scoped analysis, metric definition, dashboard, or model. |
| Stakeholder communication | Plain-language summaries, dashboard commentary, decision notes, senior-stakeholder explanations. |
| Technical collaboration | Work with engineering/data teams on pipelines, model logic, testing, or data limitations. |
| Peer review culture | Reviewed queries, documented assumptions, used version control, improved team standards. |
| Proactive improvement | Automated manual tasks, introduced validation checks, improved dashboard reliability, reduced recurring issues. |
| Data governance awareness | Communicated limitations, documented definitions, handled sensitive/business data responsibly. |
| Critical AI use | AI-assisted coding only if used responsibly and defensibly, not as a gimmick. |

The working-style story should be:

```text
I can take ambiguous business questions, model the data properly with SQL, build reliable Looker/self-serve outputs, document the logic, validate the quality, and communicate the result clearly to both technical and non-technical teams.
```

# Interview defence notes

## 38% reporting error reduction

This should mean repeated reporting errors fell after adding validation checks.

```text
Formula:
(previous reporting issue count - post-check issue count) / previous reporting issue count
```

Example defence:

```text
I defined reporting errors as validation failures found before stakeholder release, such as mismatched totals, duplicate rows, stale refreshes, incorrect joins, missing values or broken filters. I compared comparable reporting cycles before and after introducing the 15 validation checks. The issue count fell by 38%.
```

## 98% successful refreshes

This should mean dashboards or reports refreshed successfully and passed core validation checks.

```text
Formula:
successful validated refreshes / scheduled refreshes
```

Example defence:

```text
I counted a refresh as successful only if the report completed on schedule and passed the core validation checks. The 98% figure came from successful refreshes divided by scheduled refreshes across the reporting period.
```

## 8 SQL models and 6 dashboard source tables

This should mean reusable BigQuery views/tables/scripts, not one-off ad-hoc queries.

```text
SQL model = reusable query/view/table used for transformation or reporting
Dashboard source table = modelled table consumed by Looker/BI outputs
```

Example defence:

```text
The 8 SQL models were reusable BigQuery transformations, not one-off queries. Six of them became dashboard source tables used for recurring KPI reporting and self-serve analysis.
```

This should mean unique metrics with clear logic.

