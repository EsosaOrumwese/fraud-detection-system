# Trustpilot — Fraud Detection Analyst: 3 Screens

## 1. Business / problem screen

Trustpilot’s core problem is not generic “fraud analytics.” It is **platform trust protection**.

The role exists to help Trustpilot detect fraudulent behaviour, protect consumers and businesses, and preserve the integrity of its review platform. The ad says the analyst will “analyse data, spot patterns, and write detection rules” to stop fraud, while working within the Fraud & Investigations team. 

So the CV must prove evidence around:

| Trustpilot business problem          | What our CV needs to show                                                                      |
| ------------------------------------ | ---------------------------------------------------------------------------------------------- |
| Fraudulent behaviour on the platform | You can identify abnormal, suspicious or manipulative behaviour from data                      |
| Platform misuse                      | You can investigate misuse cases and turn patterns into evidence                               |
| Trust and integrity                  | You can protect a platform, customer base, or decision process from bad actors                 |
| Detection-rule development           | You can convert analysis into concrete fraud rules, thresholds or risk indicators              |
| Customer/reviewer behaviour          | You can analyse behavioural data, user patterns, accounts, activity or interactions            |
| Scaling fraud detection              | You can improve detection workflows, internal tools, databases or investigation processes      |
| Actionable reporting                 | You can produce clear reports that support fraud, legal, media, customer or internal decisions |

The strongest business-positioning phrase for this role is probably:

```text
fraud detection, behavioural pattern analysis and detection-rule development for platform integrity
```

Not:

```text
customer behaviour ML and marketing targeting
```

That Tesco framing now needs to be shifted.

---

## 2. Technical / capability screen

Trustpilot is very specific technically, but not in the same way Tesco was.

This is less about production ML ownership and more about **SQL-led fraud analysis, BigQuery/Looker reporting, detection rules, investigations, and internal fraud tooling**.

The ad directly names SQL, Google BigQuery and Google Looker for identifying fraud trends and understanding fraudulent behaviour. It also asks for proficiency writing queries and preparing reports using SQL or a similar language. 

| Technical requirement     | CV evidence we should look for                                                        |
| ------------------------- | ------------------------------------------------------------------------------------- |
| SQL queries               | SQL fraud queries, customer behaviour queries, anomaly queries, investigation queries |
| Google BigQuery           | BigQuery queries if you used BigQuery; otherwise do **not** imply it                  |
| Google Looker             | Looker reports if you used Looker; otherwise do **not** imply it                      |
| Large datasets            | 2.35B-row behaviour surface, large customer/account/activity datasets                 |
| Fraud trend analysis      | anomaly-risk outputs, known-risk case capture, fraud pattern reports                  |
| Detection rules           | rule thresholds, risk indicators, anomaly flags, fraud scoring logic                  |
| Investigation support     | case packs, high-risk account lists, suspicious behaviour summaries                   |
| Internal tools/databases  | SQL tables, feature tables, risk indicator tables, investigation datasets             |
| Data science partnership  | model outputs, validation reports, anomaly features, fraud-risk scoring               |
| Engineering collaboration | database/tool improvements, scoring pipeline improvements, monitoring checks          |

Important: for this job, **SQL and fraud rules matter more than PySpark sophistication**. PySpark can still help, but we should not make the CV sound like a data engineering CV if the job is asking for fraud detection analysis.

## 3. Working style / stakeholder screen

Trustpilot wants someone curious, analytical, proactive, able to manage multiple priorities, and comfortable working on ambiguous fraud problems. The role also involves presenting investigations to stakeholders across the department and wider company, plus supporting media, legal and customer inquiries. 

| Working-style requirement | CV evidence we should look for                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------ |
| Ambiguous problem solving | Investigated unclear behaviour patterns and converted them into structured fraud/risk analysis   |
| Clear communication       | Wrote fraud reports, model validation reports, risk memos, stakeholder recommendations           |
| Cross-functional work     | Supported fraud/risk, data science, engineering, legal, media, customer or business stakeholders |
| Proactive investigation   | Surfaced abnormal behaviour before existing rules caught it                                      |
| Self-learning             | Built fraud/anomaly logic or detection rules from unfamiliar behavioural data                    |
| Multiple priorities       | Balanced recurring reports, ad-hoc investigations, rule analysis and stakeholder requests        |
| Transparency/fairness     | Used evidence, validation and clear thresholds rather than vague judgement                       |
| Practical action          | Turned analysis into detection rules, investigation lists, risk indicators or tool improvements  |

The working-style story should be:

```text
I can investigate ambiguous fraud patterns, produce concrete SQL-backed evidence, and communicate detection logic clearly enough for fraud, data science, engineering and business stakeholders to act on.
```

The methodology says the evidence ledger should come **after proof buckets** and before scoring; its purpose is to list candidate evidence from your experience — projects, metrics, tools, datasets, decisions, stakeholders and outputs — so we can later decide what is safe, strong, weak or role-specific.

* **Trustpilot** wants fraud trend detection, SQL, BigQuery, Looker, detection rules, escalated investigations, customer/reviewer behaviour analysis, and communication across stakeholders.

Yes — absolutely. The platform name is a **positioning label**, not a sacred fixed title.

If **“Customer Behaviour ML Platform”** was our descriptive label rather than an official product name, then we should adapt it to the role’s hiring problem.

For Tesco, “Customer Behaviour ML Platform” made sense because the role was customer analytics, churn, propensity and marketing effectiveness.

For these fraud/payment roles, that title may under-sell the evidence. We can rename the same platform based on the proof we want to foreground, as long as the description and bullets stay truthful.

## Better role-specific platform names

### Trustpilot

Use something like:

```text
Fraud Detection & Behaviour Analytics Platform
```

or:

```text
Platform Behaviour Fraud Detection System
```

This fits Trustpilot because they care about fraudulent behaviour, platform misuse, detection rules, SQL, BigQuery and Looker.

### Arriva

Use:

```text
Fraud Risk & Revenue Protection Analytics Platform
```

or:

```text
Fraud Risk Analytics Platform
```

I would be careful with “Revenue Protection” unless we can support revenue-risk/recovered-value evidence. But for Arriva, that framing is highly relevant.

### Frasers

Use:

```text
Payments, Fraud & Chargeback Analytics Platform
```

only if we genuinely have payment/chargeback evidence.

If not, safer:

```text
Fraud & Customer Risk Analytics Platform
```

or:

```text
Fraud Risk Analytics Platform
```

## The rule

The experience title should answer:

> “What should the recruiter understand this project/platform as, for this role?”

So yes, we can adapt:

```text
Customer Behaviour ML Platform
```

into:

```text
Fraud Detection & Behaviour Analytics Platform
```

or:

```text
Fraud Risk Analytics Platform
```

or:

```text
Payments, Fraud & Chargeback Analytics Platform
```

But we should not adapt it into a domain we cannot defend. For example, we should not call it a **rail revenue protection platform** unless it actually involved rail/revenue protection data.

For Trustpilot, I’d probably use:

```text
Data Scientist
Fraud Detection & Behaviour Analytics Platform — Exeter, UK | May 2025 – Present
```

That keeps the same project truthful while making the role relevance much sharper.
