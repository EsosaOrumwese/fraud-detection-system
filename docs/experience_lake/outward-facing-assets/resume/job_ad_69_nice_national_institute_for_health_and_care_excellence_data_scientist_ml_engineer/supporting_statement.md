# Supporting Statement - NICE Data Scientist (ML Engineer)

I am applying for the Data Scientist (ML Engineer) role because my experience is strongly aligned with building responsible, deployable machine-learning products that turn complex data into evidence users can trust. I understand that NICE needs more than model experimentation: the role requires data pipelines, tested code, deployment, monitoring, model evaluation, governance, privacy, ethical assurance and clear communication with technical and non-technical users.

I meet the specialist knowledge requirement through a First Class BEng Mechanical Engineering degree and an MSc Data Science with Artificial Intelligence, completed with Distinction. My postgraduate work covered Python, SQL, statistics, machine learning, data preprocessing, visualisation, model evaluation and responsible interpretation. My engineering background strengthened my numerical reasoning and structured problem-solving, while my platform work gave me practical optimisation experience through threshold analysis that balanced precision, recall and review workload.

My strongest evidence is an AWS-hosted fraud and transaction decisioning platform that I built across the full ML lifecycle: ingestion, validation, feature creation, rule and model decisioning, case creation, monitoring dashboards and offline evaluation. The aim was not simply to produce a risk score, but to create a decisioning workflow where events were checked, scored, explained, turned into reviewable cases, monitored over time and improved when data quality or model behaviour changed.

I treated the first working version as an MVP: ingestion, validation, scoring and case creation came first, then I added monitoring, offline evaluation, reason-code dashboards and threshold review once the main workflow was reliable. That approach helped me make delivery decisions around what needed to work first, what could be improved later, and which controls were necessary before outputs could be trusted.

Technically, I used Python and SQL to process data, create features, validate records, score events and evaluate outputs. The deployed architecture used API Gateway and Lambda for event ingestion and validation; MSK Serverless for event movement; Docker, ECR and EKS for containerised services; Aurora PostgreSQL for cases, decisions and operational state; S3 for raw events, curated datasets, model artefacts and evaluation outputs; CloudWatch for logs, errors, latency and alarms; and EventBridge for scheduled monitoring and evaluation jobs. I used Git and GitHub for version control, GitHub Actions for linting, unit tests, Docker builds and deployment workflows, and MLflow with SageMaker for experiment tracking, model artefacts, evaluation runs and model comparison.

I treated testing and release assurance as part of the platform, not an afterthought. Before treating changes as usable, I used validation tests around ingestion, schema checks, feature creation, decision outputs and dashboard measures; unit checks for transformation and scoring logic; and smoke checks after deployment to confirm that events were accepted, validated, scored and visible in monitoring outputs. This helped protect against silent failures such as missing required fields, broken joins, unexpected category changes, failed services or dashboard measures that no longer reconciled to the source data.

The decisioning approach combined rules, model scores, thresholds and reason codes rather than relying on a black-box score. I used rule checks for high-velocity activity, unusual amounts, repeated failed attempts, missing required fields and category risk flags. I used logistic regression as an interpretable baseline, gradient-boosted tree models as stronger scoring candidates, and anomaly-detection experiments for unusual transaction patterns. Outputs included score bands, reason codes, threshold versions and case status, so users could understand whether a flag was driven by behaviour, data quality or threshold logic.

I evaluated models critically rather than relying on headline accuracy. Because fraud-style decisioning can involve class imbalance, I reviewed precision, recall, F1-score, ROC-AUC, PR-AUC, confusion matrices, false positives, false negatives and threshold effects. I also reviewed how threshold changes affected review workload, because a technically strong model can still fail operationally if it creates too many cases for users to handle. This helped connect model performance to practical decision-making.

Data engineering and data quality were central to the work. I separated raw events, validated records, features, decision outputs, case records, monitoring outputs and evaluation evidence. I built checks for missing fields, duplicate event IDs, invalid categories, failed joins, unexpected row-count movements, null rates and rejected records. I monitored event volumes, validation failures, reason-code frequency, score distributions, threshold-band movement and reviewed-case outcomes so real behavioural change could be distinguished from broken feeds, changed categories, missing fields or over-sensitive thresholds.

My workplace experience has also strengthened my data-quality judgement. At South Western Technologies & Oilfield Services Ltd, I worked in field engineering and operations analytics support, where operational records were created close to live service activity. I worked with job timings, equipment status, delays, service records, QHSE submissions, man-hour records and operational exceptions, turning field activity into structured records for post-job analysis and reporting. That experience taught me that analytical outputs are only useful when the underlying records are complete, consistent and grounded in the workflow that created them.

I also have experience with large and complex datasets beyond the platform. In a public-data project, I combined over one thousand daily business activity files into a multi-million-row dataset using Python and pandas, selected stable metrics for time-series interpretation, and communicated findings alongside policy context without overstating causation. In my MSc research, I worked with high-frequency smartphone sensor data for multi-task learning, creating model-ready windows and evaluating classification outputs while documenting limitations around sampling, class balance and generalisability.

I treated responsible AI as a design requirement. In the decisioning platform, I used reason codes, validation flags, model-version records, threshold-version records, human review for high-risk cases, documented limitations and evaluation notes so outputs could be reviewed rather than treated as unexplained scores. I also used bias checks across available operational segments such as channel, transaction type, account age band and category group. I avoided hard-coded credentials, kept configuration and secrets outside code, separated raw data from curated outputs, and used least-privilege access principles.

I would challenge deployment of an AI output where the evaluation data, bias checks, privacy controls, human-review route or model limitations were not clear enough for the decision being supported. For me, responsible AI means being able to explain what the model was trained on, what it is suitable for, where it is weak, how it was evaluated, and what human review or governance process surrounds its use.

I can communicate technical outputs clearly. My dashboards were designed around user questions: event volume, flagged cases, reason codes, validation failures, score distributions, threshold effects and review workload. Headline views gave the main position quickly, while diagnostic views allowed technical users to investigate model and data behaviour. I have also used written summaries, exception views and verbal explanations to show what data said, what was uncertain and what action was needed.

I have not held formal line management responsibility in this area, but I have set working standards through documentation and reusable workflows. I documented model purpose, features, thresholds, validation rules, dashboard measures and failure checks so another analyst or engineer could understand the workflow, rerun evaluations and challenge the output. I have also supported trainees by explaining reporting workbooks, data checks, operational definitions and exception interpretation.

I would bring to NICE ML engineering capability, data-quality discipline, statistical judgement, responsible-AI awareness and clear communication. I am motivated by using machine learning where evidence, transparency and public value matter, and I would contribute by building reliable, explainable and governed AI products that support better health and care decision-making.
