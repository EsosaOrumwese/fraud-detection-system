## 1. Requirement Being Targeted

The requirement being targeted here is the South Tyneside and Sunderland NHS Foundation Trust `Data Analyst` expectation around:
- gathering user information requirements
- communicating with directors, managers, clinicians, administrators, and service users
- explaining complex analytical outputs clearly to non-analytical professionals
- understanding what will add value to a customer requirement
- offering alternative, more useful reporting or analysis options rather than only fulfilling the first request as stated

This maps directly to the South Tyneside candidate-profile requirement that the analyst should be able to sound like someone who:
- can work with service users rather than only build in isolation
- can turn loose or vague requests into clear BI requirements
- can explain complex reporting or analytical meaning to non-technical audiences
- can recommend a better output shape when the first ask is not the most useful one

This note exists because that requirement is easy to flatten into the vague statement:
`good with stakeholders`

That is not the real burden.

The employer is asking for something sharper:
- service-facing requirement gathering
- BI translation for non-analytical users
- requirement shaping
- better-option recommendation
- practical value framing for reporting products

## 2. The Analogue On The Current Platform

The current platform does not contain a literal South Tyneside service-desk queue, directorate requirement-capture portal, or broad business-partner function, so the slice has to use an honest analogue.

The closest truthful analogue is:
- one BI reporting-product pack already built in South Tyneside `01`
- one anomaly-and-control pack already built in South Tyneside `02`
- one bounded requirement-capture surface over that same BI lane
- one service-facing translation surface that explains what the outputs mean and which reading should be preferred
- one better-option direction that shows how a vague or broad service ask should be tightened into a more useful BI product

So for this slice:
- `gathering user information requirements` maps to `one explicit requirement-capture and requirement-shaping surface over the existing BI pack`
- `communicating with non-analytical users` maps to `one service-facing explanation surface tied to the same governed BI lane`

The claim must therefore remain:
- requirement-gathering shaped
- BI-translation shaped
- better-option shaped
- careful not to imply a full stakeholder-engagement office, business-partner model, or enterprise service-design function where this slice only proves one bounded service-facing BI translation layer
