- one revised delivery-pattern output and one refinement comparison can be produced from the same Frimley lane

Important warning:

- if the inherited outputs cannot support a clean revised pattern and comparison layer, narrow the claim rather than inventing a synthetic improvement estate

## 2. Refinement-First Posture

This slice must not begin as a generic improvement or innovation slice.

The correct posture is:
- confirm the inherited product-and-support outputs first
- identify the revised delivery pattern second
- define the specific comparison against the earlier posture third
- build the revised delivery-pattern output fourth
- build the refinement comparison output fifth
- write the best-practice and caveat notes sixth
- use Python only after the inherited compact outputs have already bounded the improvement question

This matters because the Frimley responsibility is not “sound improvement-minded.” It is about refining tools and materials in practical ways that can be repeated.

## 2A. Memory And Query Discipline

This slice must be executed with explicit memory discipline.

The correct posture is:
- do not pull broad raw surfaces into pandas
- do not reopen wide raw profiling if the improvement question can be answered from Frimley `01` and `02`
- do not assume continuous improvement requires a large process-estate rebuild

The correct query discipline is:
- start with Frimley `01` and `02` compact outputs before any new materialisation
- use the product, walkthrough, support, and adoption notes first
- if a probe is needed, filter to the fields that define delivery order, support structure, or repeatability
- materialise one compact revised-pattern layer and one compact comparison layer only after the key method fields are clear
- let Python read only those compact outputs, not raw detailed source families

The default execution ceiling for this slice is:
- inherited Frimley product-and-support surfaces first
- one compact revised delivery-pattern layer second
- one compact comparison layer third
- one compact best-practice and caveat note set fourth

If a query starts behaving like a broad transformation programme, a team-method framework, or a service-improvement project rather than a bounded Frimley proof, stop and narrow it before proceeding.

Before building either the revised pattern or the comparison output, run a bounded scope gate.

The first profiling pass must answer:
- which Frimley `01` and `02` surfaces are strong enough to anchor a clean refinement story?
- what specific aspects of the delivery method can be improved honestly from those outputs?
- can the revised pattern and the comparison output both be produced from the same compact Frimley lane?
- do the row counts, fields, and current notes show that the slice can remain compact?
- is the first pass still clearly method-refinement work rather than drifting into a fake programme or team-governance claim?

Required checks:
- continuity of the chosen compact Frimley outputs
- continuity of the key delivery-order and support fields across those surfaces
- ability to define one revised pattern from the existing lane
- ability to define one bounded comparison without inventing broad organisation-wide history

Those checks should be implemented as:

- no broad row materialisation into memory

Decision rule:
- if the inherited outputs are explicit enough, proceed with the bounded improvement pack
- if not, add one compact refinement-ready reshaping layer rather than broadening the query footprint
