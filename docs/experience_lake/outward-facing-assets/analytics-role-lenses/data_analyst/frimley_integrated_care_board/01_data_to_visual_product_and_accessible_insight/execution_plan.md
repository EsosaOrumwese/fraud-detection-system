## 2. Shaped-Data-First Posture

This slice must not begin as another generic dashboard slice.

The correct posture is:
- confirm the inherited governed compact outputs first
- identify the product-ready shaping layer second
- define the shared metrics and dimensions third
- build the dashboard-style summary fourth
- build the infographic-style or concise visual-story output fifth
- write the accessible explanation and caveat notes sixth
- use Python only after the inherited compact outputs have already bounded the product question

This matters because the Frimley responsibility is not only about making a chart. It is about taking complex data through a shaping step and turning it into something non-technical users can understand.

## 2A. Memory And Query Discipline

This slice must be executed with explicit memory discipline.

The correct posture is:
- do not pull broad raw surfaces into pandas
- do not reopen wide raw profiling if the visual-product question can be answered from compact governed outputs
- do not assume product work requires a broad interactive estate or complex rendering pipeline

The correct query discipline is:
- start with compact-output profiling before any new materialisation
- use inherited summaries, reporting cuts, and audience-shaped outputs first
- if a probe is needed, filter the window and fields at scan time
- materialise one compact shaped base only after the retained metrics and dimensions are clear
- let Python read only those compact outputs, not raw detailed source families

The default execution ceiling for this slice is:
- inherited governed surfaces first
- one compact shaped product base second
- one compact dashboard summary and one compact visual-story output third
- one compact explanation and caveat note set fourth

If a query starts behaving like a full dashboard-estate rebuild or a multimedia-production project rather than a bounded Frimley proof, stop and narrow it before proceeding.

## 4. Early Scope Gate

Before building either the dashboard summary or the visual-story output, run a bounded scope gate.

The first profiling pass must answer:
- which governed compact outputs are strong enough to support one stable shaped product base?
- what metrics and dimensions are essential to both presentation surfaces?
- can the dashboard summary and the infographic-style output both be produced from the same compact shaped logic?
- do the row counts, fields, and current notes show that the slice can remain compact?
- is the first pass still clearly static analytical communication rather than drifting into fake multimedia capability?

Required checks:
- continuity of the chosen compact governed output
- continuity of retained dimensions across the candidate product surfaces
- ability to define one shaped base for both outputs
- ability to explain the outputs in accessible language without inventing extra unsupported context

Those checks should be implemented as:
- aggregate-only or compact-output probes
- inherited compact outputs where available
- no broad row materialisation into memory

Decision rule:
- if the inherited outputs are explicit enough, proceed with the bounded visual-product pack
- if not, add one compact shaping layer rather than broadening the query footprint

## 8. Shared-Logic Strategy

The dashboard summary and infographic-style output have to stay honest.

The first-pass shared-logic strategy should answer:
- what is the governed shaped base?
- which metrics and dimensions are preserved across both outputs?
- why is the visual-story surface still analytically faithful?
- why is the translated output more accessible without saying something different?

Allowed posture:
- one compact shaped analytical base feeding two clearly related presentation surfaces
- one explanation note derived from that same governed logic

Disallowed posture:
- two disconnected visual products that only loosely resemble each other
- decorative infographic language that outruns the actual evidence

Decision rule:
- every retained metric or field must earn its place in either:
  - shaped base
  - dashboard summary
  - infographic-style output
  - accessible explanation
- if a field does not support one of those purposes, drop it
