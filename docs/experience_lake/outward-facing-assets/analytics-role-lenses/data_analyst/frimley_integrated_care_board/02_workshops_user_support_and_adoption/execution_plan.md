## 1. Confirmed Working Assumptions

This plan is built around the following assumptions that must be tested immediately:
- the repo already contains enough compact Frimley `01` outputs to support one honest adoption-and-support slice without a fresh analytical rebuild
- the strongest platform analogue for the Frimley `D + E` burden is a bounded support layer over an existing product pack rather than a full enablement programme
- one demonstration-ready walkthrough and one user-support surface can be produced from the same Frimley product logic
- one adoption-improvement note can be stated from that same support pack without widening scope into a broad change-management or capability-building claim

Candidate first-pass reusable foundations:
- Frimley `01` shaped visual-product base
- Frimley `01` dashboard summary
- Frimley `01` infographic insight surface
- Frimley `01` accessible explanation note

Working assumption about the Frimley question:
- the slice should focus on one compact adoption-support chain only
- the output should prove that the product pack can be demonstrated, supported, and made easier to use
- the slice should prove workshop-and-support shaped product adoption, not literal ownership of a live training calendar, a support desk, or a full adoption programme

Important warning:
- these assumptions must be tested rather than carried forward casually
- if the inherited product surfaces cannot support a clean walkthrough and support layer, narrow the claim rather than inventing a synthetic enablement estate

## 2. Walkthrough-First Posture

This slice must not begin as a generic stakeholder or training slice.

The correct posture is:
- confirm the inherited product surfaces first
- identify the support-ready walkthrough path second
- define the likely user-friction points and practical guidance third
- build the demonstration-ready walkthrough fourth
- build the user-support or usability-friction surface fifth
- write the adoption-improvement and caveat notes sixth
- use Python only after the inherited compact outputs have already bounded the support question

This matters because the Frimley responsibility is not merely “talk to users.” It is about helping people use analytical products confidently through practical explanation and support.

## 2A. Memory And Query Discipline

This slice must be executed with explicit memory discipline.

The correct posture is:
- do not pull broad raw surfaces into pandas
- do not reopen wide raw profiling if the adoption-support question can be answered from Frimley `01`
- do not assume support work requires synthetic user-behaviour estates or large interaction logs

The correct query discipline is:
- start with Frimley `01` compact outputs before any new materialisation
- use the shaped base, dashboard summary, infographic surface, and explanation note first
- if a probe is needed, filter to the fields that define product reading order or likely user friction
- materialise one compact walkthrough layer and one compact support layer only after the key product-reading fields are clear
- let Python read only those compact outputs, not raw detailed source families

The default execution ceiling for this slice is:
- inherited Frimley product surfaces first
- one compact walkthrough layer second
- one compact user-support or usability-friction layer third
- one compact adoption-improvement and caveat note set fourth

If a query starts behaving like a full organisational adoption programme, a training-management system, or a support-desk simulation rather than a bounded Frimley proof, stop and narrow it before proceeding.

Before building either the walkthrough or the user-support surface, run a bounded scope gate.

The first profiling pass must answer:
- which Frimley `01` product surfaces are strong enough to anchor a demonstration-ready walkthrough?
- what likely user-friction points can be stated honestly from those existing outputs?
- can the walkthrough and the support surface both be produced from the same compact product logic?
- do the row counts, fields, and current notes show that the slice can remain compact?
- is the first pass still clearly support-ready static guidance rather than drifting into fake live workshop delivery or a helpdesk claim?

Required checks:
- continuity of the chosen compact Frimley `01` surfaces
- continuity of the key reading-order fields across those surfaces
- ability to define one walkthrough path from the existing product pack
- ability to define likely support prompts without inventing unobserved user behaviour

Those checks should be implemented as:
- compact-output probes
- inherited Frimley `01` outputs where available
- no broad row materialisation into memory

Decision rule:
- if the inherited product surfaces are explicit enough, proceed with the bounded adoption-support pack
- if not, add one compact support-ready reshaping layer rather than broadening the query footprint

## 5. Candidate Support Base

The first-pass support base should stay bounded and explicit.

Each component should have one stated purpose:
- inherited dashboard summary
  - provide the quick-scan entry point
- inherited visual-story surface
  - provide the guided reading order
- inherited accessible explanation
  - provide the plain-language interpretation anchor
- demonstration walkthrough layer
  - define how a user should be guided through the pack in sequence
- user-support or usability-friction layer
  - define likely confusion points and practical support prompts
- adoption-improvement note
  - define why the added support layer makes the pack easier to use
- release or repeatability checks
  - define whether the support pack is controlled enough to reuse

If inherited outputs do not support one of those components cleanly, adapt by narrowing the support layer rather than stretching the slice past its truth boundary.

Build small profile checks only for:

Goal:

- prove that the existing product pack can be extended into a bounded support layer without broad raw rebuild

### Step 2. Materialise the demonstration-ready walkthrough

Create one bounded output, for example:

This output should:
- show the recommended reading or demonstration order across the Frimley product surfaces

### Step 3. Materialise the user-support or usability-friction surface

Create one bounded output, for example:

This output should:

Write:
- the adoption-support scope note

- the adoption-improvement note
- the caveats and regeneration note

Only after the walkthrough and support surfaces are real.

## 8. Shared-Logic Strategy

The walkthrough and user-support surface have to stay honest.

The first-pass shared-logic strategy should answer:
- what inherited Frimley product surfaces are being reused?
- what reading order is being made explicit?
- which likely user-friction points are grounded in the current outputs rather than invented?
- why does the support layer improve usability without changing the analytical truth?

Allowed posture:
- one compact product pack feeding one walkthrough and one user-support layer
- one adoption-improvement note derived from that same bounded support logic

Disallowed posture:
- claiming real live workshop delivery where only support-ready materials exist
- claiming active troubleshooting history where only likely friction prompts can be supported
- drifting into broad change-management or training-programme language

Decision rule:
- every retained field or prompt must earn its place in either:
  - walkthrough
  - user-support surface
  - adoption-improvement note
- if it does not support one of those purposes, drop it
