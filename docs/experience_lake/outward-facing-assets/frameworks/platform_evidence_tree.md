# Platform Evidence Tree

## Purpose

This note records the positioning rule for using the platform across different job applications.

The platform should not be treated as several separate job-specific inventions. Each job ad may require a different emphasis, but all positioning must belong to one expanding evidence tree.

## Core Rule

There is one base platform and one evolving positioned reality.

Different job ads activate different branches of the same tree. They do not create unrelated versions of the platform.

If an element has already been established in the evidence tree, later applications should reuse it unless there is a clear reason to revise it. Do not re-extrapolate the same element into a contradictory version for another job ad.

## What This Means

When positioning the platform for a new role:

- Start from the already established platform evidence.
- Identify which part of the role requires a new branch or extension.
- Extend the tree only where the role exposes a capability not yet positioned.
- Keep domain, scale, data sources, tools, methods, and outcomes consistent with the existing tree.
- Avoid creating a new platform identity that conflicts with previous positioning.

## Established Evidence Should Stay Stable

Examples of evidence that should remain stable once established:

- platform scale, such as the 2.35 billion row credit surface;
- core data domains, such as customer, account, transaction, risk, decision, outcome, and reporting data;
- architecture posture, such as AWS-hosted storage, querying, and workflow layers;
- modelling methods, such as Logistic Regression baselines, XGBoost / gradient boosted trees, and SHAP explainability;
- experimentation methods, such as A/B, holdout, and champion/challenger testing;
- BAU model maintenance, such as drift monitoring, threshold checks, scoring refreshes, and model performance review;
- agentic AI support, such as OpenAI Codex-assisted hypothesis, feature-test, model-comparison, and evidence-summary workflows.

## Role-Specific Branches

Role positioning should expose the relevant branch of the same platform.

| Role angle | Branch emphasis |
|---|---|
| Financial Data Analyst | Governed data flows, SQL/SAS datasets, finance/risk reporting, data quality, and trusted intelligence. |
| Data Scientist | Predictive modelling, customer behaviour, experimentation, explainability, model monitoring, and business decision support. |
| Production Data Scientist / ML role | End-to-end ML lifecycle, Python/SQL/PySpark pipelines, deployment, testing, CI/CD, documentation, security, and production workflows. |

## Working Mental Model

The platform begins as a smaller base reality, but positioning expands it as an evidence tree.

A new job ad should not create a separate tree. It should ask:

> Which branch of the existing platform evidence tree answers this hiring problem?

If the role requires a capability that has not yet been positioned, create a new branch and connect it back to the existing platform story.

## Current Unified Story

The platform should be understood as:

> A customer behaviour and risk intelligence platform where large customer, account, transaction, risk, decision, and outcome datasets are turned into governed data flows, production ML workflows, explainable models, tested strategies, BAU monitoring, and business-facing insight.
