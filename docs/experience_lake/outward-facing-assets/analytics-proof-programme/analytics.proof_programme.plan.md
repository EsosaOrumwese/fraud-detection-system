## 1. Why This Programme Exists

The current analytics work is already rich enough to support strong outward-facing claims, but it is still mostly held in the form of:
- role-lens execution slices
- bounded employer-aligned proof objects
- inherited analytical outputs that snowball from earlier work

That is valuable, but it still leaves one gap:

`the current slices are strong proof fragments, but they are not yet consolidated into a smaller number of tool-visible, interview-usable, portfolio-usable proof packs`

This programme exists to close that gap.

The goal is not to create generic end-to-end dashboard projects for their own sake.

The goal is to turn the existing governed analytical work into a small number of proof packs that make it easier to:
- answer application questions with real examples
- walk through the work in interviews without sounding vague or over-rehearsed
- practice realistic data-analyst workflows using the same governed world already established in the repo
- show tool competence through the right analytical layer rather than through toy datasets or disconnected tutorials

## 2. Governing Reading Of The Current Work

The correct reading of the current analytics lane is:

- one governed platform world already exists
- one outward-facing analytics-lens system already exists
- one job-ad and candidate-profile demand surface already exists
- multiple employer-aligned slices have already been executed inside that system
- later slices often inherit preparation from earlier slices on purpose

That means the current analytics work should not be treated as:
- unrelated mini-projects
- a collection of dashboard demos
- a portfolio of independent case studies that all start from raw data

It should be treated as:
- one governed analytical proving system
- many bounded proof objects
- with deliberate inheritance between slices to reduce repeated work and keep the execution truthful

This matters because the proof packs built under this programme must preserve that truth.

---

## 3. Programme Truth Boundary

Each future proof pack must explicitly distinguish between:
- inherited analytical preparation
- new responsibility being demonstrated
- bounded local implementation for the proof pack
- wider claims that are still out of scope

So each proof pack should answer four questions up front:

1. What earlier slices or governed outputs does this pack inherit?
2. What new responsibility does this pack make visible?
3. What tool-visible outputs will be built for this pack?
4. What does this pack still not claim?

This rule prevents two common failures:
- overstating later snowball slices as if they were built from zero
- flattening the whole system into a vague "I built a dashboard" story

---

## 4. What Counts As A Proof Pack

A proof pack is not simply an extract, a dashboard, or a note.

It is a bounded evidence surface that combines:
- a real analytical problem
- a shaped analytical data layer
- one or more tool-appropriate outputs
- a clear interpretation layer
- enough control and documentation to defend the work if challenged

At minimum, a proof pack should contain:
- one problem statement
- one source and shaping summary
- one `SQL` layer or equivalent extract-definition layer
- one bounded validation or QA surface
- one stakeholder-facing reporting or analytical output
- one interpretation or briefing note
- one short "what this proves" section

Depending on the pack, the stakeholder-facing output may be:
- a `Power BI` dashboard
- an `SSRS` operational report
- an `Excel` workbook used for reconciliation or analysis review
- a small combination of these

---

## 5. Why The Tooling Has To Be Bounded

The governed world behind these analytics slices is large.

So the proof-programme rule must be:

`desktop tools work on bounded analytical layers, not on the full raw governed world`

That means:
- `SQL` should do the heavy shaping
- local extracts should be narrowed to proof-pack purpose
- `Excel` should be used for validation, reconciliation, checks, and compact analytical review
- `Power BI` should be used on shaped and bounded analytical tables
- `SSRS` should be used only where a fixed-format, repeatable, operational reporting surface is the right analogue

This is not a compromise. It is the correct analytical posture.

The proof is not:
- "I loaded the whole platform into Excel"

The proof is:
- "I knew how to shape the right analytical layer for the tool and the stakeholder need"

## 8. Execution-Lane Selection Rule

The programme should not be organised around one employer.

Instead, each build round should choose an execution lane by asking:

1. which lane currently gives the strongest inherited analytical base for the proof family?
2. which lane currently makes the snowball structure easiest to explain honestly?
3. which lane is strongest for tool-visible implementation without forcing fake build work?
4. which lane best helps cover multiple recurring job-ad requirements at once?

So the execution lane is a tactical choice.

The proof family remains corpus-wide.

Examples:
- a `trusted BI reporting` pack may use a South Tyneside-led lane because it is already rich and sequential
- a `governance and output control` pack may use a mixed lane combining South Tyneside, Guy's, Welsh Government, and Claire House surfaces
- a `stakeholder translation` pack may use South Tyneside plus Frimley plus HUC evidence rather than one employer only

That is the correct way to keep the programme broad while still building something concrete.

## 10. Role Of Excel In This Programme

`Excel` should not be used as the main heavy data engine for these proof packs.

Its strongest role is:
- reconciliation
- data-quality review
- spot-checking metrics
- compact scenario tables
- interview-friendly validation walkthroughs
- supporting worksheets for operational consumers

That means `Excel` should prove:
- careful checking
- practicality
- business-friendly review discipline

It should not be forced to prove:
- raw-scale engineering strength

---

## 11. Role Of Power BI In This Programme

`Power BI` should be the primary stakeholder-facing proof surface where the pack is about:
- management information
- dashboards
- BI translation
- decision support
- quality-monitoring visibility

It should sit on:
- bounded semantic layers
- shaped SQL outputs
- deliberately chosen measures

It should prove:
- that the analysis can be made understandable
- that the reporting logic is structured
- that the output has a defensible audience purpose

---

## 12. Role Of SSRS In This Programme

`SSRS` should be optional and selective.

It is only worth adding where the proof burden is specifically about:
- repeatable paginated reports
- scheduled operational reporting
- printable or fixed-format information products
- exception reports or compliance-style outputs

It should not be added to every proof pack just to name the tool.

The right posture is:

`use SSRS where the reporting problem is fixed-format and operational, not where Power BI already better proves the point`
